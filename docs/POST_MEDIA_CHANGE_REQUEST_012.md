# Change Request — one image attachment per post (proposal only)

Status: NOT APPROVED. No bucket, policy, table, migration, upload route or media UI has been created. Main-site coordinator and database/storage owner approval are required before implementation.

## Proposed minimum contract

- Existing `posts` rows remain the source of ownership (`author_id`) and public visibility. Propose one nullable `image_path` text field on `posts`, with server-side validation before any path change. A separate table is preferable if multiple images or lifecycle metadata become requirements; decide before writing a migration.
- Create a dedicated `post-images` Storage bucket, not shared with the AI module or other projects. Candidate maximum: one JPEG, PNG or WebP image per post, 5 MiB maximum; verify actual MIME by file signature, not filename alone. Reject SVG and executable/polyglot content. Re-encode or strip metadata if privacy review requires it.
- Candidate object key: `<owner-uuid>/<post-uuid>/<image-uuid>.<validated-extension>`. The key must be generated by trusted server code and never accepted as an arbitrary client-supplied path. No overwrite/upsert by default.
- Storage RLS proposal: authenticated upload only when `auth.uid()` matches the key owner and the referenced post's `author_id`; replacement/deletion only by that owner. Read policy should match the public-post product decision; do not expose bucket listing or unrelated objects. Use publishable/client credentials only; no service-role bypass in a browser.
- Post update action must verify that `image_path` is an approved object belonging to that post and user. Post deletion must remove its object through an authorised cleanup flow; database FK cascades do not delete Storage objects. Define retry/orphan cleanup for failed cross-service operations before enabling the feature.
- Upload workflow: create the post first, upload the validated object, then attach the confirmed path; on failure keep the text post usable and present a retry. Editing should preserve the old image until the replacement is confirmed, then clean it up. Deletion must give clear user feedback and avoid accidentally deleting someone else's object.

## Migration, security and rollback gates

1. Independently review the schema migration, bucket configuration, Storage policies, maximum file size and public/private read model. Confirm ownership and direct API rejection with ordinary authenticated users in isolation.
2. Run synthetic upload tests: valid formats; spoofed MIME; oversize; cross-user attach/delete; forged path; upload failure; edit replacement; post deletion; orphan cleanup; mobile layout. Do not use real user media.
3. Obtain separate explicit authorization for migration, Storage policy changes and deployment. None is granted by this document.
4. Rollback should disable new uploads first, keep existing post text and media references readable while objects are reconciled, then remove code/policies only after confirming no orphaned or inaccessible attachments. Never drop the image field or bucket with user media present without a preservation plan.

Supabase documents Storage RLS separately from table RLS and recommends standard uploads for small files; the 5 MiB proposal stays below its 6 MiB small-file guidance: [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), [standard uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads).
